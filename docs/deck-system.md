# デッキ・ローカル保存設計

状態: テスト済み。2026-11-16にユーザーからPR #10/#11の実機で問題なし報告を受領。PR #10はdevelopへ統合済みで、PR #11 / `feature/m1-deck-management-20261115` のbaseもdevelopへ変更した。

## 仕様
- 20枚、同名最大2枚、存在するcardIdのみ。色制限は追加しない。
- 複数デッキの作成・名称編集・複製・削除・保存・選択。無効な編集中デッキも保存できるが対戦開始は拒否。
- 検索（名前/効果）、色・種類・コストフィルター、各カードの所持数/採用数、20枚と有効性を表示。
- 既存 `DECK_LIST` は初期保存デッキのコピー元とする。編集でマスターやCPUデッキを変更しない。
- M1はオフライン試用カードを各2枚利用可能とし、M2の獲得実績と混同しない。保存済みデッキのカード配列を検証してコピーしてからシャッフル。

## 実装とデータ
`web/decks.js` はDOM非依存の検証/保存。`web/deck-ui.js` は編集バッファ、検索/フィルター、保存・選択・削除/バックアップの操作。`web/decks.css` はモーダルの縦横表示。設定メニューの「デッキ構築・保存」から開く。

保存キー `crystal-overdrive.profile.v1`:
`{schemaVersion:1, revision, decks:[{id,name,cards:[cardId]}], activeDeckId, collection:{source:'offline-starter', counts:{cardId:2}}}`。

最大30デッキ、名前32文字、カード20枚までを保存する。0〜19枚の編集中デッキも保存できるが、対戦開始は20枚/同名2枚/所有数を検証してから許可。最後のデッキを削除すると選択なしになる。編集は保存前のコピーに対して行い、現在の試合やCPUデッキは変更しない。

「選択デッキで対戦を始める」と再戦では検証済み配列を `newGame(playerDeck)` に渡す。エンジンも20枚・既知ID・同名2枚を再検証し、不正なら既存の対戦状態を変更せず拒否する。山札はコピーしてシャッフル。再起動時は保存した選択から開始し、無効/選択なしならデッキ一覧を開く。

純粋な `DeckSystem.validateDeck(cards, master, counts)` は枚数、同名超過、不明ID、所有不足を構造化して返す。現行12種は名称とIDが一対一であり、IDで採用数を数える。名前はUIへ挿入する際エスケープする。

## 保存安全性
JSON解析、文字数上限、バージョン、型、非負整数、カード/デッキIDを検証する。破損/未知のバージョンを自動上書きせず、読み取り専用の初期デッキにフォールバックし、元の読込データをエクスポートできる。既存保存のない環境では初回の保存/選択時に書き込む。

書き込み成功後だけメモリ上のプロフィールを更新する。QuotaExceeded/利用不可時は成功表示を出さず、以前の保存と編集バッファを保持する。削除失敗も確認画面に表示する。保存直前に読み込み時/直前保存時の生データと照合し、別タブの更新を検出した場合は上書きを拒否する。この照合はlocalStorageの完全な並行トランザクションではなく、同時刻の別タブ書き込みを完全には排他できない。複数端末同期・オンラインの正本には使わない。

過去のプロフィール形式はまだないため移行処理は未実装。将来の移行は非破壊の検証/バックアップから開始し、破壊的変更は承認が必要。音量などの設定保存は別タスク。
